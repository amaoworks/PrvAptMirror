# 实施路线

## MVP：手工发布带签名的软件包

MVP 必须实现：

- 可重复部署的 Docker Compose 配置；
- 基于 `aptly` 和 GPG 的按需运行 `repoctl` 容器；
- 对外暴露一个内部端口的非特权只读 Web 容器；
- 持久化的上传、Aptly、GPG 和公开仓库目录；
- 仓库初始化和公钥导出；
- 使用 `main` 组件、可配置的 Debian 系发行版；
- 为 `amd64`、`arm64`、`armhf` 和 `all` 生成索引；
- 导入前检查 DEB 元数据；
- 带签名的快照、原子发布和回滚；
- 管理员使用说明和基础仓库冒烟测试。

MVP 的完成标准是：一台全新 VPS 可以接收手工上传的 DEB，发布软件包并提供有效且带签名的 `InRelease`；一个干净的 APT 客户端无需绕过信任检查即可成功执行 `apt update`。

MVP 明确不包含：

- 自动下载上游文件；
- 镜像外部软件仓库；
- 源码构建或 Flatpak 转换；
- Web 管理界面或公开管理 API；
- 定时任务；
- 原生或模拟架构的构建节点；
- 多用户角色和审批流程。

## 第二阶段：自动获取软件包

- 在 `catalog/` 中定义软件来源、来源类型、更新策略、校验和或签名规则、目标发行版和允许架构。
- 获取 GitHub Releases 和普通网站提供的软件包。
- 使用 Aptly 镜像、过滤器和快照同步上游 APT 仓库中的指定软件包。
- 定时检查新版本，没有变化时不重复发布。
- 保存上游来源、校验和与获取时间。
- 先发布到候选快照，通过验证后再晋升为正式版本。

## 第三阶段：可重复的软件包构建

- 每个软件的打包配方存放在 `packaging/<package-name>/`。
- 使用 Debian 打包元数据从上游源码构建。
- 为每个目标发行版使用干净、隔离的构建环境。
- 尽可能使用原生节点构建 `amd64` 和 `arm64`；仅在确有需求时为 `armhf` 引入 QEMU 或原生构建节点。
- 保留 `.dsc`、`.changes`、`.buildinfo`、构建日志和源码来源信息。
- 正式发布前执行安装与升级测试。
- 将 Flatpak 视为寻找上游源码或版本信息的输入，而不是通用的 DEB 转换格式。在许可证和构建系统允许时，应从原始源码重新构建。

## 第四阶段：运维与扩展

- 快照保留与垃圾清理策略；
- 自动加密备份和恢复演练；
- 带过渡期的签名密钥轮换；
- 监控指标、结构化日志和更新失败告警；
- 可选的鉴权管理 API 或管理界面；
- 多构建节点和明确的发布审批流程。
