# 实施路线

## 第一阶段：带签名 APT 仓库基础（已完成）

第一阶段原称 MVP，已经完成并通过端到端测试：

- 可重复部署的 Docker Compose 配置；
- 基于 `aptly` 和 GPG 的按需 `repoctl` 容器；
- 非特权、只读的公开仓库 Web 容器；
- 持久化的上传、Aptly、GPG 和公开仓库目录；
- 仓库初始化、公钥导出和发行版仓库创建；
- `amd64`、`arm64`、`armhf` 和 `all` 软件包校验与索引；
- 带签名的不可变快照、原子发布和回滚；
- 静态检查以及发布、签名、多架构、更新、回滚和下载冒烟测试。

这个阶段继续作为稳定基础维护，但项目不再以 MVP 状态描述。

## 第二阶段：单管理员 Web 管理（当前阶段）

当前阶段把已有命令行管理能力安全地提供到浏览器，并增加上传和任务管理：

- 一个 Compose 项目统一编排全部服务，日常启动不要求理解内部 profile；
- `.env` 指定唯一应用数据根目录，所有绑定挂载都收敛在该目录；
- 幂等 `bootstrap` 自动创建目录与权限、首次设置令牌并初始化或复用 GPG 密钥；
- 首次启动没有默认密码，管理员使用一次性令牌在浏览器中创建密码；
- 单管理员密码登录，不提供注册和多用户；
- 安全的服务端会话、CSRF 防护、登录限速和审计日志；
- 仓库、软件包、快照、签名公钥和服务状态页面；
- 在网页创建仓库、初始化密钥、导入发布和执行回滚；
- DEB 上传、元数据预检、SHA-256、待处理文件和上传限制；
- 串行后台任务、进度、结果和脱敏日志；
- 独立 `admin-web`、无网络 `repo-worker` 和只读 `repo-web`；
- 管理服务不挂载 Docker Socket、GPG 私钥或 Aptly 数据库；
- 管理入口单独使用 HTTPS 域名或路由，不与公开仓库匿名路径混用。

详细功能、安全约束和完成标准参见 [单管理员 Web 管理](web-admin.md)，部署体验和下一实现批次参见 [统一多容器编排与首次设置](unified-deployment.md)。

### 第二阶段检查点

1. **认证与只读概览（已完成）**：Argon2id 登录、安全会话、CSRF/Origin、限速、安全头和公开仓库概览；
2. **统一编排与首次设置（范围待确认）**：单一数据根目录、幂等 bootstrap、自动 GPG 初始化、一次性令牌和 Web 创建密码；
3. **安全上传与预检**：随机文件名、大小限制、SHA-256、DEB 元数据和待处理文件；
4. **结构化任务 Worker**：无网络串行 Worker、任务状态、幂等和追加式审计；
5. **发布与回滚**：仓库创建、导入发布、快照、二次确认和回滚。

检查点 2 只改善部署基础和首次进入流程，不提前扩大上传、发布或密钥管理的 Web 权限。

## 第三阶段：自动获取软件包

- 在 `catalog/` 中定义软件来源、来源类型、更新策略、校验和或签名规则、目标发行版和允许架构；
- 获取 GitHub Releases 和普通网站提供的软件包；
- 使用 Aptly 镜像、过滤器和快照同步上游 APT 仓库中的指定软件包；
- 定时检查新版本，没有变化时不重复发布；
- 保存上游来源、校验和与获取时间；
- 先发布到候选快照，通过验证后再晋升为正式版本。

## 第四阶段：可重复的软件包构建

- 每个软件的打包配方存放在 `packaging/<package-name>/`；
- 使用 Debian 打包元数据从上游源码构建；
- 为每个目标发行版使用干净、隔离的构建环境；
- 尽可能使用原生节点构建 `amd64` 和 `arm64`，确有需求时再为 `armhf` 引入 QEMU 或原生节点；
- 保留 `.dsc`、`.changes`、`.buildinfo`、构建日志和源码来源信息；
- 正式发布前执行安装与升级测试；
- 将 Flatpak 视为寻找上游源码或版本信息的输入，而不是通用 DEB 转换格式。

## 第五阶段：运维与扩展

- 快照保留与垃圾清理策略；
- 自动加密备份和恢复演练；
- 带过渡期的签名密钥轮换；
- 监控指标、结构化日志和更新失败告警；
- 可选的多用户、角色、审批流程和第三方身份提供商；
- 多构建节点和明确的发布晋升策略。
