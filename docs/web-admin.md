# 第二阶段：单管理员 Web 管理

当前进度：检查点 1 已实现单管理员 Argon2id 登录、内存中的服务端不透明会话、CSRF/Origin 校验、登录限速、安全响应头和公开仓库只读概览。上传、任务 Worker 和发布写操作尚未接入。

## 阶段目标

第二阶段在已经完成的带签名 APT 仓库基础上增加一个仅供管理员使用的 Web 管理入口。管理员可以在浏览器中上传 DEB、创建仓库、发布软件包、查看快照并执行回滚，不再需要为日常操作登录服务器运行命令。

本阶段只支持一个管理员身份和密码登录，不实现用户注册、多用户、角色、审批流或第三方登录。公开 APT 下载与管理入口必须使用不同的域名或反向代理路由，管理入口不能直接暴露到 `repo-web`。

## 功能清单

### 登录与会话

- 使用固定的单管理员账号和密码登录；
- 由运维侧替换密码哈希 Secret 完成密码轮换，并使现有会话失效；
- 登录失败限速和渐进式延迟；
- 主动退出、会话超时和服务端会话撤销；
- 显示最近成功登录和失败登录时间，不记录密码或会话令牌。

### 仪表盘

- 显示管理服务、Worker 和公开仓库服务的健康状态；
- 显示仓库数量、软件包数量、快照数量和当前发布版本；
- 显示最近任务及其状态；
- 显示签名密钥是否已初始化、公钥指纹和到期时间；
- 显示磁盘占用及关键目录是否可写。

### 与现有命令对应的功能

| 页面操作 | 对应命令 | 风险级别 | 交互要求 |
| --- | --- | --- | --- |
| 初始化签名密钥 | `repoctl init` | 高 | 仅首次配置显示，必须二次确认 |
| 导出/下载仓库公钥 | `repoctl key export` | 低 | 只提供公钥，不提供私钥导出 |
| 创建发行版仓库 | `repoctl repo create <family> <suite>` | 中 | 展示最终仓库名并确认 |
| 查看仓库软件包 | `repoctl package list <family> <suite>` | 低 | 支持按包名、版本、架构筛选 |
| 导入并发布软件包 | `repoctl package add <family> <suite> <deb-path>` | 高 | 先展示 DEB 元数据和 SHA-256，再确认发布 |
| 查看快照 | `repoctl snapshot list <family> <suite>` | 低 | 标记当前公开快照 |
| 回滚 | `repoctl rollback <family> <suite> [snapshot]` | 高 | 展示当前与目标快照，要求二次确认 |

Web 层只能调用预先定义的结构化任务类型，不能接受任意 Shell 命令、任意 `repoctl` 参数或任意文件路径。

### 上传与待处理文件

- 只接受普通 `.deb` 文件；
- 上传到随机命名的临时文件，完成后再原子移动到待处理目录；
- 服务端限制单文件大小、总上传空间和请求时长；
- 忽略客户端提交的目录信息，显示名称与磁盘文件名分离；
- 上传完成后使用 `dpkg-deb` 读取包名、版本、架构和维护者，并计算 SHA-256；
- 发布前校验 DEB 格式、包名、版本和允许架构；
- 展示待处理文件列表、校验结果、上传时间和发布状态；
- 允许删除尚未导入的待处理文件，删除前必须确认；
- 不支持通过 URL 代下载软件包，该能力保留给后续自动获取阶段。

### 任务与审计

- 创建、导入发布、密钥初始化和回滚作为串行后台任务执行；
- 状态至少包括 `queued`、`running`、`succeeded` 和 `failed`；
- 页面可查看开始时间、结束时间、结构化结果和脱敏日志；
- 重复提交使用幂等键避免重复发布；
- 每个管理动作记录时间、动作类型、目标、结果和请求来源 IP；
- 审计日志追加写入，不能通过 Web 页面修改或删除。

## 目标架构

```text
浏览器
  │ HTTPS
  ▼
管理反向代理
  │ 仅回环地址
  ▼
admin-web ─────► var/admin/uploads
  │                 │
  │ 结构化任务       ▼
  └────────────► var/admin/jobs
                         │
                         ▼
                 repo-worker（无网络）
                    │           │
                    ▼           ▼
              Aptly/GPG      var/public
                                  │ 只读
                                  ▼
                              repo-web
```

`admin-web` 负责登录、页面、上传、只读查询和创建结构化任务；`repo-worker` 串行消费任务并复用 `repoctl` 的校验与发布逻辑。公开下载服务 `repo-web` 保持独立。

## 权限边界

| 组件 | 网络 | 可读写路径 | 明确禁止 |
| --- | --- | --- | --- |
| `admin-web` | 仅管理反代可访问 | `var/admin/`、待处理上传目录 | Docker Socket、GPG 私钥、直接写 Aptly 数据库、直接写公开仓库 |
| `repo-worker` | `network_mode: none` | Aptly 数据、GPG 私钥、待处理上传、任务目录、公开仓库 | 对外端口、任意网络访问 |
| `repo-web` | 仅公开反代可访问 | 只读 `var/public` | 上传目录、任务目录、Aptly 数据、GPG 私钥 |

不得为了从网页启动临时容器而把 `/var/run/docker.sock` 挂载到 `admin-web`。Docker Socket 等价于宿主机 root 权限，不符合本阶段的安全边界。

## 密码与会话安全

- 首次启动前由运维人员离线生成 Argon2id 密码哈希；配置只保存哈希，不保存明文密码；
- 密码哈希通过权限为 `0600` 的 Docker Secret 或宿主机文件只读挂载，不写入镜像、Git、Compose 环境变量或日志；
- 管理页面不能改写密码 Secret；密码轮换通过运维命令替换 Secret 并重启管理服务完成；
- 密码至少 14 个字符，服务端不设置会降低密码强度的截断规则；
- 登录成功后使用随机的服务端会话，Cookie 必须设置 `Secure`、`HttpOnly`、`SameSite=Strict`；
- 所有改变状态的请求都必须校验 CSRF Token，并检查 `Origin`；
- 登录接口按 IP 和账号限速，连续失败增加延迟；
- 管理入口必须使用 HTTPS，不允许通过公开 APT 下载域名复用无鉴权的路径；
- 响应设置严格 CSP、`X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer` 和禁止嵌入页面的策略。

## 上传与执行安全

- 反向代理和应用同时设置上传大小限制；
- 上传文件不使用用户原始文件名作为磁盘路径；
- 所有路径在服务端解析后必须仍位于指定上传根目录；
- Worker 只接受固定 JSON Schema 的任务，并对 `family`、`suite`、快照名和文件标识重新校验；
- Web 页面展示任务日志时进行 HTML 转义，不直接渲染包元数据中的富文本；
- 发布写操作继续使用现有跨容器文件锁，Worker 本身也只允许单任务执行；
- 失败任务不得改变当前公开快照；上传临时文件和失败任务应有保留与清理策略。

## 本阶段不包含

- 多用户、角色与权限分级；
- 用户注册、找回密码、邮箱验证码和 OAuth/OIDC；
- 公开管理 API 或供第三方使用的 API Token；
- 自动从 GitHub、网站或外部 APT 仓库下载；
- 软件包删除、仓库删除、快照垃圾回收和签名私钥下载；
- 源码构建、审批流和多节点调度。

## 实施顺序

1. 把 `repoctl` 的输出扩展为稳定的机器可读 JSON，同时保持现有 CLI 可用；
2. 实现结构化任务格式、串行 Worker、状态文件和审计日志；
3. 实现单管理员密码登录、会话与 CSRF 防护；
4. 实现仓库、软件包、快照和公钥的只读页面；
5. 实现安全上传、DEB 元数据预检和待处理文件管理；
6. 实现仓库创建、导入发布、密钥初始化和回滚；
7. 增加单元测试、鉴权测试、上传攻击用例和完整端到端测试；
8. 更新 Compose、反向代理、备份、恢复和升级文档后部署。

## 完成标准

- 未登录用户不能读取任何管理数据，也不能上传或创建任务；
- 单管理员可以在网页完成全部现有 `repoctl` 日常功能；
- 上传无效文件、越权路径、重复提交和并发写入会被可靠拒绝；
- `admin-web` 无法访问 Docker Socket、GPG 私钥和 Aptly 数据库；
- `repo-worker` 没有对外端口和网络访问能力；
- 发布失败时现有公开仓库保持可用；
- 登录限速、会话、CSRF、安全响应头和审计日志均有自动化测试；
- 从上传 DEB 到签名发布、客户端 `apt update` 和回滚的端到端测试通过。
